# Project Constitution

## 1. 제품 철학

- 마감이즈커밍은 웹툰 작가의 작업 관리와 창작 자료 정리를 돕는 정적 웹 애플리케이션이다.
- 사용자는 달력, 메모, 북마크, 노동요, 포모도로와 CLIP 미리보기를 한곳에서 안정적으로 사용해야 한다.
- 가장 중요한 가치는 사용자 데이터 보존, 기존 기능의 안정성, 단순하고 실용적인 사용 흐름이다.
- 기능을 추가한다는 이유로 인증, 저장, 배포 방식을 함께 바꾸지 않는다.
- 검증하지 않은 자동화나 시각적 완성도를 이유로 기존 작업 흐름을 깨뜨리지 않는다.

## 2. Architecture 원칙

- GitHub Pages에서 실행되는 브라우저 애플리케이션을 기본 배포 형태로 유지한다.
- Firebase가 활성화된 환경에서는 사용자 메타데이터의 원본을 Firestore에 둔다.
- Google Drive는 이미지와 미리보기 같은 큰 사용자 파일을 맡고, Firebase 비활성 환경에서는 기존 JSON 저장 대체 경로를 유지한다.
- 파일 선택 권한, 로컬 핸들, 재생 객체와 타이머 같은 브라우저 실행 상태는 저장 데이터와 구분한다.
- 기능 모듈은 자신의 UI와 동작을 맡고 저장 방식 자체를 소유하지 않는다.
- 저장 서비스는 기능의 화면과 재생 동작을 소유하지 않는다.
- 기존 저장 스키마, DOM ID와 공개 `window.*` 계약은 대체 경로와 마이그레이션이 검증되기 전까지 유지한다.
- 한 파일은 하나의 주된 책임과 변경 이유에 집중한다.

영구 계약은 `docs/architecture/`에 기록한다.

## 3. 문서 체계

- 공통 AI 작업 방식은 루트 `AGENTS.md`를 따른다.
- 프로젝트 작업 전에 이 문서를 읽는다.
- 영구 기능·구조 계약은 `docs/architecture/`에 기록한다.
- 현재 실제 코드 위치와 책임은 `docs/96_src_map.md`에 기록한다.
- 아직 시작하지 않은 Sprint 후보는 `docs/97_next_sprint.md`에 기록한다.
- 현재 승인된 Sprint는 `docs/98_sprint_plan.md`에 기록한다.
- 가장 최근 Task 결과는 `docs/99_recent_task.md`에 기록한다.
- 완료된 Sprint 기록은 `docs/completed/`에 보존한다.
- 같은 내용을 여러 문서에 복사하지 않고 기준 문서를 링크한다.
- 루트 `current_task.md`는 최신 작업 결과를 사용자에게 전달하는 호환 보고서로 유지한다.

## 4. 구현 원칙

- 요청과 현재 Sprint 범위 안에서만 구현한다.
- 기존 구조와 데이터 흐름을 실제 코드로 확인한 뒤 변경한다.
- 리팩토링 중에는 기능, 저장 스키마와 사용자 동작을 바꾸지 않는다.
- 구조 변경과 신규 기능 구현을 같은 Sprint에 섞지 않는다.
- 순수 로직을 먼저 분리하고 테스트한 다음 브라우저·외부 서비스 경계를 이동한다.
- 기존 전역 계약을 제거할 때는 사용처, 초기화 순서와 대체 인터페이스를 함께 검증한다.
- 새 파일이나 책임 변경은 `docs/96_src_map.md`에 반영한다.
- 관련 없는 사용자 파일과 dirty worktree 변경을 수정하거나 stage하지 않는다.

## 5. 작업과 검증

- 작업 전에 `docs/98_sprint_plan.md`와 관련 Architecture 문서를 확인한다.
- JavaScript 변경은 `npm run lint`와 관련 테스트를 실행한다.
- 문서·코드 형식은 `npm run format:check`로 확인한다.
- 모든 변경은 `git diff --check`와 변경 파일 검토를 거친다.
- 정적 검사는 실제 Firebase, Drive, 파일 선택, YouTube 재생과 청각 QA를 대신하지 않는다.
- 실행하지 않은 외부 환경 검증은 미검증으로 명시한다.
- Task가 끝나면 `docs/99_recent_task.md`와 `current_task.md`를 갱신한다.
- Sprint가 끝나면 Architecture, Source Map과 `docs/completed/` 기록을 동기화한다.
